# 눈으로만 확인되는 것

UI/UX 재설계에서 테스트로 옮길 수 있는 것은 전부 옮겼다. 남은 건 **브라우저가 실제로 칠한 결과**를
보는 것뿐이다. `pnpm dev` → http://localhost:5173

## 이미 테스트가 지키는 것 (다시 볼 필요 없음)

| 한때 눈으로 봐야 했던 것                            | 지금 지키는 테스트                                                                                        |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 셸 폭은 글자 크기에 안 움직이고 가독폭은 움직이는가 | `layoutScale.test.ts` — 프레임은 px, 측정은 em이라는 **단위**를 단언                                      |
| 건너뛰기 링크가 첫 Tab에 보이는가                   | `cssEmissionOrder.test.ts` — `focus:not-sr-only`가 `sr-only` **뒤에** 방출되는지                          |

| NVDA가 표를 "표, N열 M행"으로 읽는가                | 같은 파일 — `role="table"` / `columnheader` / `row`가 살아 있는지                                         |

## 이제 브라우저가 자동으로 확인하는 것

`pnpm dev` 한 쪽에 띄워 두고 `pnpm test:visual`. Chromium을 실제로 띄워 11개를 확인한다.

| 확인                    | 내용                                                                |
| ----------------------- | ------------------------------------------------------------------- |
| 각 폭에서 콘텐츠 프레임 | 390·768·1024 = 뷰포트 / 1280 = 1180 / 1440 = 1320 / 1920 = 1560     |
| 글자 배율 0.85·1.0·1.3  | **프레임은 안 움직이고 가독폭은 움직인다**(598→704→915px)           |
| 모바일 390px 가로 넘침  | 5개 경로에서 `scrollWidth ≤ clientWidth`                            |
| 건너뛰기 링크           | 첫 Tab에 포커스되고 **실제로 그려진다**(`clipPath: none`, 116×38px) |
| 경로 이동 포커스        | `/knowledge`·`/progress` 이동 시 `<main>`으로                       |
| 다크 모드 인쇄          | `#0e1116`/`#e6e9ee` → `#fff`/`#000`, `--fs-root: 11pt`              |

**이 스위트가 첫 실행에서 실제 버그를 하나 잡았다.** 경로 포커스 효과가 StrictMode의 이중 호출
때문에 시작 시점에 발동해 `<main>`이 이미 포커스를 갖고 있었고, 그래서 **첫 Tab이 건너뛰기 링크를
지나쳤다** — 건너뛰기 링크가 존재하는 이유 그 자체가 무력화돼 있었다. `stylesheetLayers`도
`cssEmissionOrder`도 내내 통과했는데, 둘 다 CSS에 대해 틀린 말을 하지 않았기 때문이다. 버그는
사용자가 키를 누르기도 전에 포커스를 옮긴 자바스크립트에 있었다. "카운트하지 말고 값을 비교하라"가
고친 방법이다(`AppShell`의 `prevPath`).

## 여전히 눈이 필요한 것

자동화가 값을 재는 것까지는 하지만, **보기 좋은지**는 재지 못한다.

### 1. `--spacing` 스윕 — **닫힘**

간격 한 단계는 이제 사용자 설정이다(`--sp-base`, 조밀/보통/여유). 「조용히 헐거워졌는가」는 더 이상
한 값을 놓고 묻는 질문이 아니고, 세 값이 서로 다른 픽셀을 만드는지는
`layout.visual.test.ts`의 «changes the rhythm of a painted page»가 실제로 칠해진 페이지에서 잰다.
남은 건 세 단계 중 **어느 것이 기본값이어야 하는가**이고, 그건 사용자가 써 보고 고를 문제다.

### 2. Windows 고대비 모드 — Chromium 에뮬레이션은 통과

`forcedColors: 'active'`로 플레이 화면을 확인했다: 카드·옵션 행·버튼 경계가 전부 `currentColor`로
다시 그려지고, 톤 배지는 채움이 지워진 뒤에도 **낱말과 글리프**로 남는다(`● 정상`·`⚠ 경고`).
와이어 항목의 왼쪽 심각도 띠는 다른 테두리와 같은 색이 되지만, 심각도 배지가 그 말을 하고 있으므로
잃는 정보가 없다 — 배지가 존재하는 이유가 그것이다. 채널 태그를 알약에서 `label-caps`로 내린 것이
여기서도 이득이다(§19).

**여전히 눈이 필요하다.** Chromium의 에뮬레이션은 실제 Windows 강제 팔레트와 같지 않다.
설정 › 접근성 › 고대비에서 남은 하나만 직접 볼 것: **포커스 링이 `CanvasText`로 보이는가.**

### 3. 넓은 화면에서 «비어 보이는가» — **닫힘: 3열로 가지 않는다**

브라우저로 쟀다. 1920에서 정보 열은 1114px이고 내용은 읽기 폭 상한(`--w-play-col: 52em`)에 걸려
832px에서 멈춘다 — 오른쪽으로 **281px**이 남는다(2560에서는 652px).

그런데 비어 보이던 것은 가로가 아니라 **세로**였고, 그 원인이 사라졌다. T0에서 상황 열은 헤드라인·
소식 3건·«최근 결과» 뿐이라 아래가 300px쯤 비었는데, 지금은 **«전 턴 대비 변화»**가 T1부터 그
자리를 채운다(1920에서 열이 y≈840까지 찬다). 남은 가로 281px은 읽기 폭 상한이 **의도적으로** 만든
여백이다 — 「44em을 넓히지 않는다」와 같은 규칙이고, 넓히면 한국어 장문이 더 읽기 어려워진다.

그래서 피드 상주 열은 **더하지 않는다.** 이미 읽기 상한에 걸린 열에서 폭을 떼어 오게 되고,
레이아웃 경우의 수가 두 배가 되며, 피드 탭과 기능이 겹친다. 2560 이상에서 다시 비어 보이면 그때
재평가한다 — 가산적인 변경이라 나중에 해도 안전하다는 판단은 여전히 유효하다.
